# Review a source-local skill

Check whether its owner, application scope and required inputs are clear. Confirm that reference entry is sufficient to find the necessary source without installing unrelated skills. Trace cross-source dependencies through the caller's selected bindings.

For a new or reorganized knowledge collection, inspect the actual document tree as well as the index graph using the [organization reference](../../../references/authoring/index.json). For filesystem sources, check that area indexes live in their own reference directories, not just sibling JSON files at the root. Follow representative reader tasks into different owner areas and check that the questions, specifications and evidence that exist are discoverable there. Reject an undifferentiated pile of substantive documents, including one hidden under a generic folder or behind a nested index. Do not reject a genuinely focused leaf area or require extra levels solely because its document count increased. Keep shared records authoritative in one location and check the links from affected areas after moves.

Repeat the content review inside each affected branch. A first-level split is not sufficient when its broad questions/specification/evidence files still mix independently changing subjects. Test both decisions: a change to an independent subworkflow should stay with its own documents, while one coherent policy should not be scattered across unnecessary directories. Accept mixed depths, parent-owned shared contracts and cohesive peer documents. Record the consequential split/keep reasons separately from the path validator result; directory shape and file counts cannot establish semantic ownership.

Review the actual change for duplicated policy, invented acceptance conditions, arbitrary limits, fixed model choices, and unrequested approval steps. Preserve specific user requirements. A concrete conditional rule is useful only when the task justifies it.

Use a representative task when behavior changed. Keep unsuccessful observations and the original artifact; distinguish package validity, model behavior and product acceptance. A limitation disclosed in documentation does not resolve a mandatory requirement gap.
