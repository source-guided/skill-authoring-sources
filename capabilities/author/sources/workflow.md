# Create and maintain a source-local skill

Start from the real task, the source owner's responsibility, and any selected authoring guidance. Confirm whether this skill belongs in the current source. Reuse existing owner material instead of creating a competing policy or universal rule from one example.

Define the capability's purpose, applicable context, inputs, expected result and relevant limits. Keep its entry short and route optional details through the source's reference index. Place domain policy, examples and tests with the owning source. Other domains are connected through references rather than copied into the skill.

Before writing a collection of source or project documents, read the organization guidance through the [authoring reference area](../../../references/authoring/index.json). Identify the owner areas in the actual task and locate their existing content. Organize both the body documents and their reference routes; do not treat writing several Markdown files or a single complete index as sufficient structure. A short capability within one existing area does not require a new hierarchy.

Create the skill under this source's internal capability directory and register its entry and workflow as discoverable references. Do not create a global plugin entry, installation hook or user-wide skill registration. The source selection enables contextual use, not global activation.

When changing a skill, inspect existing consumers and current user requirements. Preserve accepted choices, model configuration and authorization. Update discovery metadata when purpose or location changes; keep content and observations out of the index.

Verify the source participation contract and the affected behavior. For meaningful decision changes, use a fresh, bounded task without prior answers or evaluator hints. Separate a confirmed requirement mismatch from a conditional interpretation or missing source. Tests should observe decisions or outcomes, not match the wording of this guide.

## Give judgment useful inputs

Assume the model can choose among reasonable approaches. Organize open-ended guidance around the context that changes a decision, the outcomes to preserve and observations that can challenge the choice. Keep examples optional and scoped. Avoid accumulating event-to-solution branches from individual failures. Detailed instructions remain appropriate for exact contracts, permission boundaries and fragile operations where deviation has a concrete consequence; identify that reason.

Make the source entry and capability workflow discoverable before detailed leaves. Explain the questions supporting references help answer without making every reference mandatory. Review whether a real task can miss a material branch despite finding one relevant leaf. Keep task-specific acceptance and failure examples in the consumer's evaluation workspace.
